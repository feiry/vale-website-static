How it's built

Microsoft 365 — where COMMs works

Teams channel“Valeindonesia.com Update – Request”. Requests dropped in 1-Submitted; status & preview links posted back as Adaptive Cards with an Approve button.
SharePoint document libraryHolds the request folders & the form templates. No file syncing to any laptop.

Azure VM — Vale tenant (always-on)

Teams Bot endpointPublic HTTPS in Azure. Receives the chat commands.
Assistant (conversation)Understands the request, confirms before production, writes the replies. Decides when — never deploys by itself.
Operator service (deterministic)Reads files via Graph → detect type → validate → build → deploy. Every action logged. This is what touches the site.
Files read via Microsoft Graph API   Deploys via Azure Storage   One Azure AD identity

Target — the website

Preview (dev)Every change lands here first for approval.
Production — www.valeindonesia.comPublished only after the requester approves.

What it covers  /  Safe by design

  • News articles — bilingual, rich text + photos
  • Documents / PDFs — reports, statements, press releases
  • Job vacancies — add / remove lokers
  • Page edits — text, stats, images
  • New pages — reuse a layout with new content
  • Preview first — always dev before production
  • Human approval gate — requester approves go-live
  • Automatic validation — layout can't be broken
  • Backup & rollback — every change reversible
  • Full audit trail — submitted → live, logged

Why this design

Company-standard & robust. Everything lives in Microsoft Teams and Vale's Azure tenant — no third-party chat, no files synced to a personal laptop. The assistant handles the conversation; a separate, auditable service performs the actual deploys. COMMs' experience is unchanged — same forms, same Teams folder, same approve-the-preview step.
